# Logic App 17 — Abusing Workflow Edit Access to Read Blob Content

![Category](https://img.shields.io/badge/Category-Cloud%20Misconfiguration-red?style=flat-square)

> **TL;DR** — A user with read-only access to a Storage Account and Container (but no access to the blobs themselves) had write access to a Logic App. By editing the workflow to add an Azure Blob Storage connector, the Logic App's own connection permissions were abused to read blob content the user's identity could not access directly.

## Scenario

Let's log into the Azure Portal using the credentials provided and start enumerating. On enumerating the account, we find the user has read permissions on the Storage Account and Container, but not on the blobs inside the container. Searching for "Logic App" reveals the user has permission to read and write the Logic App workflow.

---

## Overview

### Why Does Write Access to a Logic App Matter Here?

A Logic App workflow executes using its own configured connections — which may have broader permissions than the identity editing the workflow. If a user can edit the workflow but not directly read the target resource, they can insert a new action into the workflow that performs the read on their behalf, then surface the result back to themselves (e.g., via an HTTP response).

> 💡 **Hint:** The permission gap is between the user's identity and the Logic App's connection.

## Steps to Reproduce

### Step 1 — Enumerate Access

Log in to the Azure Portal and enumerate available resources. The user has read access to the Storage Account and Container, but not to the blobs inside. The user also has read/write access to a Logic App workflow.

### Step 2 — Open the Logic App Designer

Search "Logic Apps" in the search bar and select the Logic App, then click **Logic App Designer** to view the workflow.

### Step 3 — Add a Blob Storage Action

Insert a new step by clicking the **+** button, select **"Add an action,"** and search for **"Azure Blob"** in the search bar. Select **"Azure Blob Storage"** and choose **"Get blob content (V2)"** from the Actions tab.

### Step 4 — Configure the Connection and Blob Path

Select an available connection to connect to the Blob Storage, then specify the blob path by clicking the folder icon at the right end of the input field and selecting the container and blob.

### Step 5 — Surface the Output via Response

Open the **Response** action, and in the Body field, click **"Add dynamic content,"** select **"File Content,"** and save the workflow.

## Key Points During Flag Finding

| # | Observation | Why It Matters |
|---|-------------|-----------------|
| 1 | **Write access to the workflow bridged the permission gap** | The user's identity couldn't read the blob directly, but the Logic App's own connection could — editing the workflow let the user borrow that access. |
| 2 | **The Blob connector's connection was more privileged than the user** | This is the core of the abuse: a service connection with broader rights than the identity managing it. |
| 3 | **The Response action was the exfiltration path** | Without wiring the blob content into the HTTP response, the data would have stayed inside the workflow run and not been visible to the user directly. |
| 4 | **No blob-level read permission was ever granted to the user** | The entire flag retrieval happened without the user's own identity ever touching the blob — all access was proxied through the Logic App. |

## Impact

- With appropriate permissions in the Logic App, we could manipulate the Logic App to interact with other services and perform malicious activity.

---

## Impact in a Real-Time Environment

### 🔴 Privilege Escalation via Workflow Editing
Any identity with write access to a Logic App can insert new actions that leverage the Logic App's own connections — effectively inheriting permissions the identity does not hold directly.

### 🔴 Sensitive Data Exposure via Blob or Other Connected Services
In this lab, the Logic App's Blob connector exposed file content. In production, the same technique could expose contents of databases, key vaults, or other connected services if the Logic App's connections have access to them.

### 🟠 Silent Abuse With No Direct Resource Access
Because the abuse happens entirely through the Logic App's connections, it may not appear in the audit logs of the target resource (e.g., the Storage Account) under the attacking user's identity — complicating detection.

### 🟠 Reusable Attack Pattern Across Any Connector
This is not limited to Blob Storage. Any connector available in Logic Apps (SQL, Key Vault, SharePoint, Service Bus, etc.) could be added the same way if the Logic App's connection has access to it.

---

## Why We Need to Secure This

**1. Write Access to a Logic App Is Effectively Write Access to Its Connections**
Granting "Contributor" or workflow-edit rights on a Logic App implicitly grants the ability to use every connection already configured on that Logic App — regardless of the editor's own permissions on those underlying resources.

**2. Connections Are Often More Privileged Than Necessary**
Logic App connections are frequently set up with broad access for convenience during development and never scoped down before reaching production.

**3. The Attack Requires No Specialized Tooling**
As with the earlier Logic App labs, this entire exploitation happened inside the Azure Portal's built-in Designer — no external tools or scripts required.

---

## Remediation

| Control | Action |
|---------|--------|
| 🔐 **Restrict Workflow Edit Access** | Limit who can edit Logic App workflows separately from who can view run history or trigger them. Treat edit access as equivalent to access on every connection configured in the workflow. |
| 🪪 **Scope Connections to Least Privilege** | Configure Blob Storage (and other) connections with the minimum access needed — e.g., read-only, scoped to a specific container — rather than account-wide access. |
| 🎯 **Use Managed Identity Per Logic App** | Prefer Managed Identity connections scoped via RBAC at the resource level over shared connection strings or broadly-scoped service accounts. |
| 📊 **Monitor Workflow Edits** | Enable diagnostic logging on Logic App changes and alert on new actions/connectors being added, especially by identities without direct access to the resource being connected. |
| 🔍 **Periodically Review Configured Connections** | Audit each Logic App's connections against the actual permissions required by its business function, removing unnecessary access. |

---

## How This Helps During Incident Response

- **Workflow version history shows exactly what changed.** Logic Apps retain versions of the workflow definition — comparing versions quickly reveals when and what action was added.

- **Run history reveals what data was accessed.** The Blob action's run history shows the exact blob path accessed and the content returned, scoping the extent of data exposure.

- **Connection audit logs identify the true accessor.** Since the read happens via the Logic App's connection rather than the user's identity, IR teams should correlate Logic App run timestamps with connection-level access logs — not just user identity logs — to see the full picture.

- **Improved IR playbooks.** This pattern should prompt responders to check Logic App edit history whenever investigating unexpected data access to a connected resource, even if the accessing identity shows no direct permissions on that resource.

# Logic App 17 — Abusing Workflow Edit Access to Read Blob Content

![Category](https://img.shields.io/badge/Category-Cloud%20Misconfiguration-red?style=flat-square)

> **TL;DR** — A user with read-only access to a Storage Account and Container (but no direct access to the blobs themselves) had write access to a Logic App workflow. By editing the workflow to add an Azure Blob Storage connector, the Logic App's own connection permissions were abused to read blob content the user's identity could not access directly.

## Scenario

Let's log into the Azure Portal using the credentials provided and start enumerating. On enumerating the account, we find the user has read permissions on the Storage Account and Container, but not on the blobs inside the container. Searching for "Logic App" reveals the user has permission to read and write the Logic App workflow.

---

## Overview

### Why Does Write Access to a Logic App Matter Here?

A Logic App workflow executes using its own configured connections — which may have broader permissions than the identity editing the workflow. If a user can edit the workflow but not directly read the target resource, they can insert a new action into the workflow that performs the read on their behalf, then surface the result back to themselves (e.g., via an HTTP response).

The core vulnerability: **permission delegation through automation**. The Logic App's connections are trusted to access resources on behalf of the workflow execution, not based on who edited it. By inserting a "Get Blob Content" action, the user leverages the Logic App's connection credentials rather than their own identity.

> 💡 **Hint:** The permission gap is between the user's identity and the Logic App's connection permissions.

### Step 1 — Enumerate Access

Log in to the Azure Portal using the provided credentials and enumerate available resources:
- The user has **read access** to the Storage Account
- The user has **read access** to the Container
- The user has **NO access** to the blobs inside the container
- The user has **read/write access** to the Logic App workflow

### Step 2 — Open the Logic App Designer

1. Search **"Logic Apps"** in the Azure Portal search bar
2. Select the Logic App from the results
3. Click **"Logic App Designer"** to view and edit the workflow

<img width="1857" height="888" alt="image" src="https://github.com/user-attachments/assets/c1a0adb1-cf78-419a-a4d3-10b4d982ba86" />

### Step 3 — Add a Blob Storage Action

1. Click the **+** button to insert a new step
2. Select **"Add an action"**
3. Search for **"Azure Blob"** in the search bar
4. Select **"Azure Blob Storage"** from the connector options
5. Choose **"Get blob content (V2)"** from the available actions tab

**Why V2?** Newer versions of connectors often have improved capabilities and reduced legacy security issues.

### Step 4 — Configure the Connection and Blob Path

1. Select an **available connection** to authenticate with the Blob Storage
2. Specify the **blob path** by:
   - Clicking the **folder icon** at the right end of the input field
   - Selecting the target **container**
   - Selecting the **blob file** to read
  
<img width="1864" height="863" alt="image" src="https://github.com/user-attachments/assets/3179c8ff-c3ed-4f99-a602-41f4f945adbb" />

The Logic App will now attempt to read the blob using its own configured connection identity.

### Step 5 — Surface the Output via Response Action

1. Open the **Response** action (the HTTP response trigger output)
2. In the **Body field**, click **"Add dynamic content"**
3. Select **"File Content"** from the dynamic content options
4. **Save the workflow**

<img width="1905" height="798" alt="image" src="https://github.com/user-attachments/assets/7f5806d5-f4b2-48ce-9a20-0dcc4badc154" />

This step is critical — it converts the blob content from an internal workflow variable into an HTTP response that the user can see in their browser.

### Step 6 — Trigger and Retrieve the Flag

1. Copy the trigger URL from the **"When a HTTP request is received"** trigger step
2. Paste the URL into your browser address bar
3. Send the HTTP GET request
4. The response body contains the flag fetched from the blob

## Key Points During Flag Finding

| # | Observation | Why It Matters |
|---|-------------|-----------------|
| 1 | **Write access to the workflow bridged the permission gap** | The user's identity couldn't read the blob directly, but the Logic App's own connection could — editing the workflow let the user borrow that access. |
| 2 | **The Blob connector's connection was more privileged than the user** | This is the core of the abuse: a service connection with broader rights than the identity managing it. |
| 3 | **The Response action was the exfiltration path** | Without wiring the blob content into the HTTP response, the data would have remained internal to the workflow run. The Response action made it visible to the unauthenticated trigger caller. |
| 4 | **No blob-level read permission was ever granted to the user** | The entire flag retrieval happened without the user's own identity ever touching the blob — all access was proxied through the Logic App's managed connection. |
| 5 | **HTTP trigger requires no authentication** | The "When a HTTP request is received" trigger in Logic Apps is typically public-facing, allowing anyone with the URL to trigger the workflow and receive its output. |

---

## Impact

- **Privilege Escalation:** Write access to a Logic App becomes equivalent to read access on every resource the Logic App can connect to.
- **Data Exfiltration:** Sensitive data stored in blobs, databases, or key vaults can be extracted if the Logic App has access to them.
- **Unauthorized Operations:** The Logic App's connections can perform actions (write, delete, modify) on behalf of the editing user, beyond the user's own permissions.

---

## Impact in a Real-Time Environment

### 🔴 Privilege Escalation via Workflow Editing
Any identity with write access to a Logic App can insert new actions that leverage the Logic App's own connections — effectively inheriting permissions the identity does not hold directly. This is a **transitive trust** issue: the Logic App is trusted by its connections, and editing the Logic App transfers that trust.

### 🔴 Sensitive Data Exposure via Blob or Other Connected Services
In this lab, the Logic App's Blob connector exposed file content. In production, the same technique could expose contents of:
- SQL databases (via SQL Server connector)
- Key Vault secrets (via Key Vault connector)
- SharePoint documents (via SharePoint Online connector)
- Service Bus messages (via Service Bus connector)
- Any other resource the Logic App's connection can reach

### 🟠 Silent Abuse With No Direct Resource Access Logs
Because the abuse happens entirely through the Logic App's connections, it may not appear in the audit logs of the target resource (e.g., the Storage Account) under the attacking user's identity — complicating detection and forensics.

### 🟠 Reusable Attack Pattern Across Any Connector
This is not limited to Blob Storage. **Every connector available in Logic Apps** could be added the same way if the Logic App's connection has access to it — creating multiple exfiltration and lateral movement paths.

### 🟠 HTTP Trigger Exposure
Public-facing HTTP triggers on Logic Apps often require no authentication, allowing any user with the trigger URL to invoke the workflow and receive its output — potentially including sensitive data.

---

## Why We Need to Secure This

**1. Write Access to a Logic App Is Effectively Write Access to Its Connections**
Granting "Contributor," "Logic App Contributor," or workflow-edit rights on a Logic App implicitly grants the ability to use every connection already configured on that Logic App — regardless of the editor's own permissions on those underlying resources.

**2. Connections Are Often More Privileged Than Necessary**
Logic App connections are frequently set up with broad access for convenience during development and never scoped down before reaching production. A "Storage Account Contributor" connection grants access to all containers and blobs, not just the ones the workflow actually needs.

**3. The Attack Requires No Specialized Tooling**
As with earlier Logic App labs, this entire exploitation happened inside the Azure Portal's built-in Designer UI — no external scripts, tools, or APIs required. Any user with basic Azure Portal access can execute this attack.

**4. HTTP Triggers Are Inherently Unauthenticated**
By default, "When a HTTP request is received" triggers in Logic Apps have no built-in authentication, making them ideal for exfiltrating data to an external attacker or an attacker's own session.

## Remediation

| Control | Action |
|---------|--------|
| 🔐 **Restrict Workflow Edit Access** | Limit who can edit Logic App workflows separately from who can view run history or trigger them. Treat edit access as equivalent to direct access on every resource the Logic App's connections can reach. Use role-based access control (RBAC) with granular roles like "Logic App Contributor" (edit workflows) vs. "Reader" (view only). |
| 🪪 **Scope Connections to Least Privilege** | Configure Blob Storage connections with the minimum access needed — e.g., read-only to a specific container, rather than account-wide Contributor access. Use managed identities with custom roles that grant permissions at the blob or container level, not the storage account level. |
| 🎯 **Use Managed Identity Per Logic App** | Prefer Managed Identity connections scoped via RBAC at the resource level over shared connection strings, shared keys, or broadly-scoped service accounts. Assign each Logic App its own managed identity with a custom role for least-privilege access. |
| 🔌 **Authenticate and Authorize HTTP Triggers** | If the Logic App's HTTP trigger outputs sensitive data, require authentication (e.g., Azure AD OAuth, API Key) on the trigger itself. Avoid public-facing triggers for workflows that handle sensitive data. |
| 📊 **Monitor Workflow Edits** | Enable diagnostic logging on Logic App changes and alert on new actions/connectors being added, especially by identities without direct access to the resource being connected. Correlate Logic App edit events with subsequent data access in audit logs. |
| 🔍 **Periodically Review Configured Connections** | Audit each Logic App's connections against the actual permissions required by its business function, removing unnecessary access. Document why each connection is needed. |
| 📋 **Establish Approval Workflows for Edits** | For production Logic Apps, require approval before workflow edits are deployed, especially if they involve new connectors or actions on sensitive resources. |

## How This Helps During Incident Response

- **Workflow version history shows exactly what changed.** Logic Apps retain versions of the workflow definition — comparing versions quickly reveals when and what action was added, and by whom.

- **Run history reveals what data was accessed.** The Blob action's run history shows the exact blob path accessed, the timestamp, and the content returned, scoping the extent of data exposure.

- **Connection audit logs identify the true accessor.** Since the read happens via the Logic App's connection rather than the user's identity, incident response teams should correlate Logic App run timestamps with connection-level access logs (e.g., Storage Account audit logs) — not just user identity logs — to see the full picture.

- **Trigger URL analysis.** Check if the Logic App's HTTP trigger URL was accessed by unexpected users or external IPs. If so, the workflow was invoked externally, and any sensitive data in the Response action was exposed.

- **Improved IR playbooks.** This pattern should prompt responders to check Logic App edit history whenever investigating:
  - Unexpected data access to a Storage Account or other resource
  - Cases where the accessing identity shows no direct permissions on that resource
  - Any unusual Logic App run activity

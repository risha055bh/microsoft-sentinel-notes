> **TL;DR** — An Azure Logic App is configured to trigger when a Storage Queue reaches a specific message count. A low-privilege user with queue write access can add the required number of messages, fire the workflow, and retrieve a sensitive flag written back into the queue — entirely from within the Azure Portal with no external tools.

## Scenario

Logic Apps use connectors that perform defined actions when triggered. When misconfigured or when the trigger URL is exposed, they could reveal sensitive data. The goal here is to **abuse the Storage Queue message connector and obtain the flag**.

---

## Overview

### What is a Queue Message-Based Trigger?

When a new message is added to the queue, the **"Queue" trigger** activates the Logic App and starts the workflow execution. It acts as the starting point for the workflow. In this case, the Logic App is configured to trigger only when a **specific number of messages** exist in the queue — making the message count itself the attack surface.

> 💡 **Hint:** Number of messages in the queue.

### Step 1 — Log in to the Azure Portal

Log in to the Azure Portal using the provided credentials. After login, enumerate what access is available by navigating to **Subscriptions → Resources**.

We find the user has access **only to Storage Accounts**. On further enumeration, we discover the user has **permission to read and write queue messages** on the storage account.

### Step 2 — Navigate to the Storage Queue

Go to the Storage Account → **Storage Browser** → expand **Queues** → open the queue (`asdjheyq789`).

Click **"Add message"** and enter any random text. Repeat to add a **second message**. Wait approximately **30 seconds**, then refresh the queue view.

## Key Points During Flag Finding

| # | Observation | Why It Matters |
|---|-------------|----------------|
| 1 | **Message count was the trigger, not a URL or parameter** | No interception needed — simply writing 2 messages to the queue was enough to fire the workflow. |
| 2 | **Enumeration of permissions was the first pivot** | The account had scoped storage-only access. Discovering queue read/write rights revealed the entire attack path. |
| 3 | **The flag appeared inside the queue, not in the browser** | Output was written back as a queue message. Checking only HTTP responses or the wrong storage service would have missed it entirely. |
| 4 | **Waiting and refreshing was required** | Logic App queue triggers poll on an interval. The flag only appeared after ~30 seconds and a manual refresh. |
| 5 | **Message content was irrelevant — only count mattered** | Any random text triggered the workflow, confirming the condition was purely quantitative with no content validation. |
| 6 | **No external tools needed** | The entire attack was completed inside the Azure Portal's built-in Storage Browser. Zero additional tooling required. |

## Impact in a Real-Time Environment

### 🔴 Unauthorized Workflow Triggering
Any user or identity with queue write permissions can trigger the Logic App at will — including triggering it at scale, repeatedly, or at a chosen time. This bypasses any intended business logic around when the workflow should run.

### 🔴 Sensitive Data Exposure via Queue Messages
In this lab, the Logic App wrote the flag back into the queue. In production, Logic Apps triggered by queue messages often write sensitive outputs — API responses, processed records, internal tokens — back to storage. An attacker with queue access can read those outputs directly.

### 🟠 Denial of Service via Queue Flooding
A malicious actor with write access can flood the queue with thousands of messages, causing the Logic App to trigger repeatedly and at high frequency — exhausting run quotas, hitting downstream API rate limits, and generating significant unexpected Azure costs.

### 🟠 Logic App as a Proxy for Privileged Actions
If the triggered Logic App performs actions the attacker's identity cannot do directly — such as writing to a database, sending emails, or calling internal APIs — abusing the queue trigger effectively grants those privileges to anyone who can write a message.

### 🟡 Lateral Movement via Queue-Connected Workflows
Queue-triggered Logic Apps often sit at the boundary between systems. Triggering them with attacker-controlled message content can probe or interact with connected systems the attacker has no direct access to.

### 🟡 Audit and Compliance Risk
If a Logic App processes regulated data (PII, financial records, health data) and can be triggered by low-privilege queue writes, an attacker can cause that regulated data to be processed, copied, or exposed — creating compliance violations under GDPR, HIPAA, and PCI-DSS even without directly accessing the data.

## Why We Need to Secure This

**1. Queue Write Permission Is Frequently Under-Estimated as a Risk**
Teams commonly grant broad storage permissions without considering that a queue-triggered Logic App converts those permissions into workflow execution rights. Write access to a queue is not just a storage permission — it is effectively a trigger permission for any Logic App listening to that queue.

**2. The Attack Requires No Specialised Tools or Skills**
This entire exploitation happened inside the Azure Portal with zero external tooling. Any insider, compromised low-privilege account, or misconfigured service principal with queue write access can reproduce this attack. The barrier to exploitation is extremely low.

**3. Logic App Triggers Have No Built-In Rate Limiting by Default**
Azure Logic Apps do not enforce execution rate limits out of the box. A queue flood can cause unbounded trigger executions — each potentially performing expensive or sensitive downstream actions — until the consumption plan quota is exhausted or costs spiral.

**4. Output Written Back to Storage Is Readable by the Same Identity**
If the Logic App writes results (including sensitive data) back to the same storage account the attacker already has access to, the attacker can read those results directly. The queue becomes both the input and output channel for data exfiltration.

**5. Misconfigured Permissions Are Difficult to Detect Without Proper Logging**
Without Logic App run history monitoring and storage queue access logging, there is no signal that the workflow was triggered unexpectedly. The attack leaves no trace in network logs or identity audit logs beyond the standard queue write events — which may not be monitored at all.

## Remediation

| Control | Action |
|---------|--------|
| 🔐 **Least Privilege on Queue Access** | Restrict queue write permissions to only the identities that legitimately need to enqueue messages. Use Azure RBAC roles at the queue level, not the storage account level. |
| 🪪 **Use Managed Identity for the Logic App** | The Logic App should authenticate to the queue using its own Managed Identity — not a shared access key or connection string that could be reused by other identities. |
| 🔢 **Validate Message Content, Not Just Count** | If the Logic App must use a count-based trigger, add a Condition action to validate message content before executing sensitive workflow steps. |
| ⚡ **Enable Concurrency and Rate Limit Controls** | Configure Logic App concurrency settings and add throttling to prevent queue flooding from causing unbounded workflow executions. |
| 📊 **Enable Storage Queue Diagnostic Logging** | Log all queue read/write operations to Azure Monitor. Alert on unexpected write spikes, writes from unusual identities, or first-time access from new IPs. |
| 🛡️ **Enable Microsoft Defender for Storage** | Detects anomalous queue activity including bulk message insertion and access from unexpected sources in real time. |
| 🔍 **Audit Storage Permissions Regularly** | Periodically review who has write access to queues connected to Logic Apps. Remove any identities that no longer require access. |

## How This Helps During Incident Response

- **Logic App Run History is your first stop.** Every execution is logged with its trigger time and inputs. During IR, the run history tells you exactly when the threshold was hit, how many runs were triggered, and what actions each run performed — immediately scoping what the attacker caused the workflow to do.

- **Queue message logs reveal the attacker's writes.** Azure Storage diagnostic logs capture every message insertion with the caller's identity, IP address, and timestamp. Correlating these with Logic App run times shows precisely which messages caused the trigger.

- **Unexpected queue messages are IOCs.** In a real incident, messages inserted by an identity that does not normally write to that queue — or at an unusual time — are strong indicators of abuse. The message content and insertion metadata are forensic artefacts.

- **The Logic App's output messages are evidence.** If the workflow wrote results back to the queue (as in this lab), those messages reveal what data the Logic App processed and exposed during the attack — critical for assessing breach scope.

- **Knowing the threshold is key for triage.** IR teams who know the Logic App fires at a specific message count can look for that exact pattern in queue logs — a sudden write of N messages from a single identity — rather than hunting broadly across all storage activity.

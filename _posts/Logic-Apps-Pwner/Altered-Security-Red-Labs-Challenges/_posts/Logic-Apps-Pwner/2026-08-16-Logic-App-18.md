# Logic App 18 — Modify Workflow and Abuse Storage Queue

> **TL;DR** — A user with read-only access to a Storage Account and Queue (but no access to the messages themselves) had read/write access to a Logic App workflow. By editing the workflow to add an Azure Queue connector, the Logic App's own connection permissions were abused to read queue messages the user's identity could not access directly.

## Scenario

Sometimes the user we compromised can have permission to edit the workflow of the Logic App. The goal here is to **abuse the user's permission on the Logic App and read the flag from the Storage Queue**.

---

## Overview

### What is a Logic App Workflow?

A Logic App workflow is a visual representation and implementation of a business process or integration scenario in Azure Logic Apps. It defines the steps, actions, and conditions that are executed in a specific sequence to automate a particular workflow. As with the Blob Storage scenario, the workflow's own connections can hold permissions broader than the identity editing it — and those permissions can be borrowed by inserting new actions.

> 💡 **Hint:** The permission gap is between the user's identity and the Logic App's connection.

## Steps to Reproduce

### Step 1 — Enumerate Access

Log in to the Azure Portal using the credentials provided and start enumerating. On enumerating the account, we find the user has read permissions on the Storage Account and Queue, but not on the messages inside the queue — and has read/write permission on the Logic App workflow.

### Step 2 — Open the Logic App Designer

Search "Logic Apps" in the search bar and select the Logic App, then click **Logic App Designer** to view the workflow.

### Step 3 — Add a Queue Action

Insert a new step by clicking the **+** button, select **"Add an action,"** and search for **"Azure Queue"** in the search bar. Select **"Azure Queues"** and choose **"Get messages"** from the Actions tab.

### Step 4 — Configure the Connection and Queue

Select an available connection to connect to the Storage Queues, then specify the queue by clicking the drop-down at the right end of the input field and selecting the name of the queue.

Now that we've fetched the queue message, to output/display it we can use the **Response** action. Open the Response action, and in the Body field, click **"Add dynamic content,"** select **"Body,"** and save the workflow.

## Key Points During Flag Finding

| # | Observation | Why It Matters |
|---|-------------|-----------------|
| 1 | **Write access to the workflow bridged the permission gap** | The user's identity couldn't read the queue messages directly, but the Logic App's own connection could — editing the workflow let the user borrow that access. |
| 2 | **"Get messages" was the correct action, not "Get blob content"** | Choosing the right connector for the target resource type (Queue vs Blob) mattered — each Azure Storage service has its own dedicated connector actions. |
| 3 | **The Response action was again the exfiltration path** | Without wiring the queue message body into the HTTP response, the retrieved data would have stayed inside the workflow run. |
| 4 | **No queue-message-level read permission was ever granted to the user** | All access was proxied through the Logic App's connection, not the user's own identity. |

## Impact

- With appropriate permissions on the Logic App, we could manipulate the Logic App to interact with other services and perform malicious activity.

---

## Impact in a Real-Time Environment

### 🔴 Privilege Escalation via Workflow Editing
Any identity with write access to a Logic App can insert new actions that leverage the Logic App's own connections — effectively inheriting permissions the identity does not hold directly, whether the target is Blob, Queue, Table, or File storage.

### 🔴 Sensitive Data Exposure via Queue Messages
In production, queue messages often carry order data, processing tokens, or internal state information. An attacker with only workflow-edit access can extract this without ever being granted direct queue-read permissions.

### 🟠 Consistent Attack Pattern Across Storage Services
This lab confirms the technique demonstrated on Blob Storage generalizes to Queue Storage — and by extension, to any Azure Storage connector (Table, File Share) available in Logic Apps.

### 🟠 Silent Abuse With No Direct Resource Access
Because the read happens through the Logic App's connection, the attacking user's identity may never appear in the Storage Queue's own access logs — complicating detection if only resource-level logs are monitored.

---

## Why We Need to Secure This

**1. Write Access to a Logic App Is Effectively Write Access to Its Connections**
As with the Blob Storage case, granting workflow-edit rights on a Logic App implicitly grants the ability to use every connection already configured on that Logic App.

**2. Storage Queues Are Easy to Overlook in Access Reviews**
Teams often review Blob container permissions closely but pay less attention to Queue-level access, assuming queue contents are transient or low-value — which is not always true.

**3. The Attack Requires No Specialized Tooling**
As with the earlier Logic App labs, the entire exploitation happened inside the Azure Portal's built-in Designer — no external tools or scripts required.

---

## Remediation

| Control | Action |
|---------|--------|
| 🔐 **Restrict Workflow Edit Access** | Limit who can edit Logic App workflows separately from who can view run history or trigger them. Treat edit access as equivalent to access on every connection configured in the workflow. |
| 🪪 **Scope Connections to Least Privilege** | Configure Storage Queue connections with the minimum access needed — e.g., read-only, scoped to a specific queue — rather than account-wide access. |
| 🎯 **Use Managed Identity Per Logic App** | Prefer Managed Identity connections scoped via RBAC at the resource level over shared connection strings or broadly-scoped service accounts. |
| 📊 **Monitor Workflow Edits** | Enable diagnostic logging on Logic App changes and alert on new actions/connectors being added, especially by identities without direct access to the resource being connected. |
| 🔍 **Periodically Review Configured Connections** | Audit each Logic App's connections against the actual permissions required by its business function, removing unnecessary access — this includes Queue, Table, and File connections, not just Blob. |

---

## How This Helps During Incident Response

- **Workflow version history shows exactly what changed.** Comparing Logic App workflow versions quickly reveals when a new Queue action was added.

- **Run history reveals what data was accessed.** The "Get messages" action's run history shows the exact queue accessed and the message content returned, scoping the extent of data exposure.

- **Connection audit logs identify the true accessor.** Since the read happens via the Logic App's connection rather than the user's identity, IR teams should correlate Logic App run timestamps with connection-level access logs — not just user identity logs.

- **Improved IR playbooks.** This pattern reinforces that any Azure Storage service (Blob, Queue, Table, File) connected to a Logic App should be checked whenever investigating unexpected data access, even if the accessing identity shows no direct permissions on that specific resource.

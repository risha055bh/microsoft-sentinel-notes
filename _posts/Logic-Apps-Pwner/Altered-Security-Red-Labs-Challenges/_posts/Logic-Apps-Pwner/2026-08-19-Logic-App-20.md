# Logic App 19 — Abusing Workflow Edit Access to Read File Share Content

> **TL;DR** — A user with read-only access to a Storage Account and File Share (but no direct access to the files themselves) had write access to a Logic App workflow. By editing the workflow to add an Azure File Storage connector, the Logic App's own connection permissions were abused to read file content the user's identity could not access directly.

## Scenario

Let's log into the Azure Portal using the credentials provided and start enumerating. On enumerating the account, we find the user has read permissions on the Storage Account and File Share, but not on the files inside the file share. Searching for "Logic App" reveals the user has permission to read and write the Logic App workflow.

---

## Overview

### Why Does Write Access to a Logic App Matter Here?

A Logic App workflow executes using its own configured connections — which may have broader permissions than the identity editing the workflow. If a user can edit the workflow but not directly read the target resource, they can insert a new action into the workflow that performs the read on their behalf, then surface the result back to themselves (e.g., via an HTTP response).

Unlike the earlier Logic App Blob challenge, this lab targets **Azure File Shares** — a shared file storage service commonly used for enterprise file synchronization. The attack pattern remains identical: **permission delegation through automation**.

> 💡 **Hint:** The permission gap is between the user's identity and the Logic App's File Storage connection permissions.

## Key Points During Flag Finding

| # | Observation | Why It Matters |
|---|-------------|-----------------|
| 1 | **Write access to the workflow bridged the permission gap** | The user's identity couldn't read the file directly, but the Logic App's own connection could — editing the workflow let the user borrow that access. |
| 2 | **The File Storage connector's connection was more privileged than the user** | This is the core of the abuse: a service connection with broader rights than the identity managing it. |
| 3 | **The Response action was the exfiltration path** | Without wiring the file content into the HTTP response, the data would have remained internal to the workflow run. The Response action made it visible to anyone with the trigger URL. |
| 4 | **No file-level read permission was ever granted to the user** | The entire flag retrieval happened without the user's own identity ever touching the file — all access was proxied through the Logic App's File Storage connection. |
| 5 | **HTTP trigger exposes file content without authentication** | The "When a HTTP request is received" trigger in Logic Apps is typically public-facing, allowing anyone with the URL to trigger the workflow and receive its output, including file contents. |
| 6 | **File Shares are often less-monitored than Blob Storage** | Many organizations focus security hardening on Blob Storage but leave File Shares with default-permissive access, making this attack vector more viable. |

---

## Impact

- **Privilege Escalation:** Write access to a Logic App becomes equivalent to read access on every resource the Logic App can connect to.
- **Data Exfiltration:** Sensitive files stored in Azure File Shares can be extracted if the Logic App has access to them.
- **Unauthorized Operations:** The Logic App's connections can perform actions (write, delete, modify) on behalf of the editing user, beyond the user's own permissions.

---

## Impact in a Real-Time Environment

### 🔴 Privilege Escalation via Workflow Editing
Any identity with write access to a Logic App can insert new actions that leverage the Logic App's own connections — effectively inheriting permissions the identity does not hold directly. This is a **transitive trust** issue: the Logic App is trusted by its connections, and editing the Logic App transfers that trust.

### 🔴 Sensitive Data Exposure via File Share or Other Connected Services
In this lab, the Logic App's File Storage connector exposed file content. In production, the same technique could expose contents of:
- Configuration files with database connection strings
- Application secrets stored in shared drives
- PII (Personally Identifiable Information) in archived files
- Financial or healthcare records
- Source code or intellectual property

### 🟠 Silent Abuse With No Direct Resource Access Logs
Because the abuse happens entirely through the Logic App's connections, it may not appear in the audit logs of the target resource (e.g., the Storage Account) under the attacking user's identity — complicating detection and forensics.

### 🟠 Reusable Attack Pattern Across Any Connector
This is not limited to File Shares. **Every connector available in Logic Apps** could be added the same way if the Logic App's connection has access to it — creating multiple exfiltration and lateral movement paths.

### 🟠 Public-Facing HTTP Triggers
Public-facing HTTP triggers on Logic Apps often require no authentication, allowing any user with the trigger URL to invoke the workflow and receive its output — potentially including sensitive file contents, configuration data, or secrets.

### 🟠 File Share Permissions Often Overly Permissive
Azure File Shares are frequently provisioned with broad access for convenience in hybrid scenarios (on-premises and cloud file sharing). If a Logic App's managed identity is granted too much access, this creates a high-impact attack surface.

---

## Why We Need to Secure This

**1. Write Access to a Logic App Is Effectively Write Access to Its Connections**
Granting "Contributor," "Logic App Contributor," or workflow-edit rights on a Logic App implicitly grants the ability to use every connection already configured on that Logic App — regardless of the editor's own permissions on those underlying resources.

**2. Connections Are Often More Privileged Than Necessary**
Logic App connections are frequently set up with broad access for convenience during development and never scoped down before reaching production. A "Storage Account Contributor" connection grants access to all file shares and files, not just the ones the workflow actually needs.

**3. The Attack Requires No Specialized Tooling**
This entire exploitation happened inside the Azure Portal's built-in Designer UI — no external scripts, tools, or APIs required. Any user with basic Azure Portal access can execute this attack.

**4. HTTP Triggers Are Inherently Unauthenticated**
By default, "When a HTTP request is received" triggers in Logic Apps have no built-in authentication, making them ideal for exfiltrating data to an external attacker or an attacker's own session.

**5. File Shares Are Often Forgotten in Security Reviews**
Organizations typically focus hardening efforts on databases and key vaults but overlook File Shares, which can contain equally sensitive data. Logic Apps connecting to File Shares silently multiply this risk.

## Remediation

| Control | Action |
|---------|--------|
| 🔐 **Restrict Workflow Edit Access** | Limit who can edit Logic App workflows separately from who can view run history or trigger them. Treat edit access as equivalent to direct access on every resource the Logic App's connections can reach. Use role-based access control (RBAC) with granular roles like "Logic App Contributor" (edit workflows) vs. "Reader" (view only). |
| 🪪 **Scope Connections to Least Privilege** | Configure File Storage connections with the minimum access needed — e.g., read-only to a specific file share or directory, rather than account-wide Contributor access. Use managed identities with custom roles that grant permissions at the file share or directory level, not the storage account level. |
| 📁 **Separate File Shares by Sensitivity** | Isolate sensitive files into dedicated File Shares with stricter access controls. Use separate storage accounts for different sensitivity levels if possible. |
| 🎯 **Use Managed Identity Per Logic App** | Prefer Managed Identity connections scoped via RBAC at the resource level over shared connection strings, shared keys, or broadly-scoped service accounts. Assign each Logic App its own managed identity with a custom role for least-privilege access. |
| 🔌 **Authenticate and Authorize HTTP Triggers** | If the Logic App's HTTP trigger outputs sensitive data, require authentication (e.g., Azure AD OAuth, API Key) on the trigger itself. Avoid public-facing triggers for workflows that handle sensitive files. |
| 📊 **Monitor Workflow Edits** | Enable diagnostic logging on Logic App changes and alert on new actions/connectors being added, especially by identities without direct access to the resource being connected. Correlate Logic App edit events with subsequent data access in audit logs. |
| 🔍 **Periodically Review Configured Connections** | Audit each Logic App's connections against the actual permissions required by its business function, removing unnecessary access. Document why each connection is needed and what resources it should access. |
| 📋 **Establish Approval Workflows for Edits** | For production Logic Apps, require approval before workflow edits are deployed, especially if they involve new connectors or actions on sensitive resources. |
| 📋 **Implement Conditional Access** | If possible, use Azure AD Conditional Access policies to restrict Logic App editing to specific networks, devices, or times of day. |

## How This Helps During Incident Response

- **Workflow version history shows exactly what changed.** Logic Apps retain versions of the workflow definition — comparing versions quickly reveals when and what action was added, and by whom.

- **Run history reveals what data was accessed.** The File Storage action's run history shows the exact file path accessed, the timestamp, and the content returned, scoping the extent of data exposure.

- **Connection audit logs identify the true accessor.** Since the read happens via the Logic App's connection rather than the user's identity, incident response teams should correlate Logic App run timestamps with connection-level access logs (e.g., Storage Account audit logs) — not just user identity logs — to see the full picture.

- **Trigger URL analysis.** Check if the Logic App's HTTP trigger URL was accessed by unexpected users or external IPs. If so, the workflow was invoked externally, and any sensitive file content in the Response action was exposed to those IPs.

- **File access timeline.** Correlate Logic App run times with Storage Account file access logs to determine exactly which files were read and when.

- **Improved IR playbooks.** This pattern should prompt responders to check Logic App edit history whenever investigating:
  - Unexpected data access to a File Share or Storage Account
  - Cases where the accessing identity shows no direct permissions on that resource
  - Any unusual Logic App run activity
  - Potential lateral movement from a compromised user account

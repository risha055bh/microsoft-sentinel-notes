## Scenario

In certain scenarios, the compromised user might own the Logic App or have permission to read the workflow of the Logic App. This can reveal sensitive data hardcoded in the workflow template. The goal here is to **abuse the user's read permissions on the Logic App and obtain the flag**.

---

## Overview

### What is a Logic App Workflow?

A Logic App workflow is a visual representation and implementation of a business process or integration scenario in Azure Logic Apps. It defines the steps, actions, and conditions that are executed in a specific sequence to automate a particular workflow. Behind the visual designer, every workflow is backed by a **JSON definition** — and that JSON is fully readable by anyone with Reader access to the resource.

> 💡 **Hint:** Sometimes code contains interesting stuff.

## Key Points During Flag Finding

| # | Observation | Why It Matters |
|---|-------------|-----------------|
| 1 | **Reader access alone was enough** | No execution, trigger, or Contributor rights were needed — read access to the Logic App resource exposed the entire workflow definition. |
| 2 | **Code View exposed what the Designer hides** | The visual Designer renders the workflow step by step, but Code View reveals the raw JSON, including any hardcoded strings not obvious in the visual layout. |
| 3 | **The flag was static, not runtime-generated** | Unlike a queue-trigger scenario, no workflow execution was required — the secret was sitting in the definition itself. |
| 4 | **No secure parameter or Key Vault reference was used** | The value was hardcoded directly in plaintext rather than referenced via a secure parameter, `@parameters()`, or Key Vault integration. |

## Impact in a Real-Time Environment

### 🔴 Sensitive Data Exposure via Workflow Definition
Any identity with Reader access on a Logic App can view its complete workflow JSON, including hardcoded connection strings, API keys, tokens, or credentials — without needing to trigger or execute the workflow at all.

### 🔴 Credentials Extend Beyond Azure
Many Logic Apps integrate with third-party SaaS platforms (Slack, Salesforce, SendGrid, Twilio, etc.). A hardcoded API key for one of these services extends the blast radius of the compromise entirely outside the Azure tenant.

### 🟠 Exposure Through ARM Templates and Deployment History
Logic App definitions are ARM templates under the hood. Secrets hardcoded into them are also exposed through deployment history exports and, if the template was ever committed to source control, through the Git history as well.

### 🟠 Low Barrier to Discovery
Unlike credential harvesting via memory dumps or token theft, this attack requires nothing more than a Read role and a few clicks in the portal — making it one of the easiest ways to escalate from low-privilege read access to real credential exposure.

### 🟡 Persistence via Silent Modification
An identity with Contributor rights on the Logic App could go further, modifying the workflow to add a backdoor action (e.g., forwarding processed data to an external endpoint) without necessarily triggering obvious alerts.

---

## Why We Need to Secure This

**1. Logic App Definitions Are Read-Accessible by Design**
Reader-level RBAC roles are commonly granted broadly for visibility purposes. Few teams realize that Reader access on a Logic App also grants full visibility into its workflow JSON — including any hardcoded secrets.

**2. Hardcoding Secrets Is a Common Shortcut**
Developers frequently hardcode connection strings, API keys, and tokens directly into Logic App parameters during development and never migrate them to secure storage before the workflow reaches production.

**3. No Warning or Validation by Default**
Azure does not natively warn or block deployment of a Logic App containing plaintext secrets in its definition, unless Azure Policy is explicitly configured to detect this pattern.

**4. Secrets Persist Beyond the Immediate Workflow**
Once hardcoded, a secret remains in deployment history and ARM template exports even after the workflow itself is edited — meaning remediation requires more than just updating the current version.

## Remediation

| Control | Action |
|---------|--------|
| 🔐 **Never Hardcode Secrets** | Use **Azure Key Vault** integration or secure parameters (`securestring`) instead of embedding secrets directly in the workflow JSON. |
| 🪪 **Use Managed Identity** | Configure Logic App connectors to authenticate via Managed Identity rather than static credentials or connection strings. |
| 🎯 **Apply Least Privilege on Logic App Access** | Restrict Reader and Contributor roles on Logic Apps to only the identities that genuinely need visibility or edit access. |
| 🔍 **Audit Workflow Definitions Regularly** | Periodically export and scan Logic App JSON definitions for hardcoded secrets using tools like TruffleHog or `git-secrets`. |
| 📜 **Enable Azure Policy for Secret Detection** | Use Azure Policy to flag or block deployments containing plaintext secrets in Logic App parameters. |
| ♻️ **Rotate Any Previously Hardcoded Credentials** | Even after remediation, rotate any secret that was ever hardcoded — it may still exist in deployment history or logs. |

---

## How This Helps During Incident Response

- **Faster root-cause identification.** Knowing that Logic App workflows can contain hardcoded secrets gives responders a quick pivot point when investigating how an attacker obtained credentials for an unrelated resource.

- **Scoped containment.** If a Logic App is found to expose a secret, IR teams can immediately rotate that specific credential and check Azure Activity Logs for any resource accessed using it — rather than assuming a broader compromise.

- **Better detection engineering.** This pattern highlights the value of alerting on **Reader-level access to Logic App Code View** or **ARM template export** actions, which are often overlooked in favor of monitoring Owner/Contributor activity.

- **Improved IR playbooks.** Responders can build a checklist step to always review Logic App JSON definitions for hardcoded secrets as part of any Azure compromise investigation, rather than treating it as an afterthought.

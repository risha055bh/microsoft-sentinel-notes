> **TL;DR** — An exposed Azure Logic App HTTP trigger accepts a user-controlled `{name}` parameter with no authentication or input validation. By intercepting the request via Burp Suite and changing `name` to `admin`, the workflow silently writes a sensitive file to a connected Azure File Share — accessible via a leaked SAS URL.

## Scenario

Logic Apps use connectors that perform defined actions when triggered. When misconfigured or when the trigger URL is exposed, they could reveal sensitive data. The goal here is to **abuse the exposed trigger URL and obtain the flag**.

---

## Overview

### What is a SAS URL (Shared Access Signature URL)?

A SAS URL is a URL that contains a shared access signature token. It allows secure access to specific resources within an Azure Storage account for a limited period, **without requiring the account key**. SAS URLs provide a way to grant granular access permissions to clients or applications without exposing the storage account keys.

## Steps to Reproduce

### Step 1 — Trigger the Logic App URL

Copy the Logic App trigger URL and open it in a browser. On observing the URL, we notice a `{name}` parameter present in it. After pasting the URL, there is **no output** in the browser.

### Step 2 — Connect to Storage Using the SAS URL

Use the SAS URL provided via the **Azure Storage Explorer Tool**.

1. Open the Storage Explorer Tool
2. Click on **"Open Connect Dialog"**
3. Select **"Storage account or service"**
4. Select **"Shared Access Signature URL"**
5. Paste the SAS URL, click **Next**, and connect

### Step 3 — Intercept the Request with Burp Suite

Copy the trigger URL. Make sure **Burp Suite Interceptor is ON**, then paste the URL into the browser.

1. Intercept the outbound request in Burp Suite
2. Change the `name` parameter value to **Admin**
3. Send the request to **Repeater**
4. Forward the modified request

## Key Points During Flag Finding

These are the critical observations made throughout the exercise — directly relevant to spotting and exploiting this class of vulnerability in real engagements:

| # | Observation | Why It Matters |
|---|-------------|----------------|
| 1 | **No browser output ≠ no action** | The Logic App silently wrote to storage. Always check backend side-effects, not just HTTP responses. |
| 2 | **`{name}` parameter was the entry point** | User-controlled parameters flowing into Logic App workflows are manipulation targets. The name hinted at a role context — `admin` was the natural test value. |
| 3 | **Burp Suite Interceptor was essential** | The URL had to be modified mid-flight. Without a proxy, in-browser parameter changes aren't possible on GET requests this way. |
| 4 | **SAS URL gave a parallel path into storage** | Even without touching the trigger, the SAS URL alone granted direct File Share access — bypassing Logic App logic entirely. |
| 5 | **Refreshing Storage Explorer was necessary** | The file appeared only after a refresh, reflecting Logic App async execution. Don't assume no result means no action. |
| 6 | **Repeater enabled controlled iteration** | Burp's Repeater allowed rapid re-testing with different parameter values without re-intercepting each time. |

## Impact in a Real-Time Environment

This vulnerability pattern is not limited to CTF labs. Each element maps directly to real-world production risks:

### 🔴 Unauthorized Data Access and Exfiltration
An attacker who obtains a valid SAS URL can download any file in the connected storage share — including customer PII, financial records, internal documents, or credentials stored as files — without authenticating through Azure AD or triggering identity-based alerts.

### 🔴 Privilege Escalation via Parameter Tampering
If the Logic App uses the `name` parameter to determine workflow branches or permissions, replacing it with values like `admin` can unlock higher-privilege actions — writing sensitive data, modifying configurations, or triggering downstream APIs that should be restricted.

### 🟠 Silent Data Writes to Storage
Because the Logic App produces no browser output, an attacker may exfiltrate data or plant malicious content in storage without any immediate signal. Security teams relying only on HTTP-level monitoring would miss this entirely.

### 🟠 Unauthenticated Workflow Abuse
A publicly exposed trigger with no authentication can be called by anyone. This opens the door to repeated triggering — causing cost spikes from Logic App runs, exhausting downstream API rate limits, and potentially disrupting connected business processes.

### 🟡 Lateral Movement Across Connected Services
Logic Apps are integration hubs. A single compromised trigger can interact with everything the Logic App is connected to — databases, email, Microsoft Teams, SharePoint, third-party APIs — turning one misconfiguration into a broad lateral movement opportunity.

### 🟡 Compliance and Regulatory Exposure
Unauthorized access to storage containing personal or financial data triggers mandatory breach reporting under GDPR, HIPAA, and PCI-DSS. The resulting fines and reputational damage can significantly outweigh the cost of the controls that would have prevented the incident.

## Why We Need to Secure This

### 1. SAS URLs Are Credentials — Treat Them Like Secrets

A SAS URL carries embedded authentication. Once it leaks — through source code, chat messages, logs, or API responses — any person who possesses it has the exact permissions it encodes, for as long as it remains valid. Unlike Azure AD tokens, SAS tokens do not expire on user de-provisioning and have no central revocation mechanism. The only remediation after a leak is to rotate the storage account key, which breaks all integrations relying on existing SAS tokens.

### 2. Logic App HTTP Triggers Are Internet-Accessible by Default

Azure Logic Apps support Azure AD authentication on HTTP triggers, but it is **not enabled by default**. Every publicly accessible trigger without authentication is effectively an open API endpoint. Attackers and automated scanners routinely probe for these within hours of deployment.

### 3. User-Controlled Input Must Never Be Trusted

Any value arriving from a query parameter, request header, or body that flows into a Logic App action — especially storage operations — must be validated against a strict allowlist. Allowing arbitrary values to determine workflow paths or storage targets is an architectural flaw. The Logic App must never rely on caller-supplied values to make privilege decisions.

### 4. The Blast Radius of a Compromised Logic App Is Extremely Large

Logic Apps routinely hold active connections to databases, storage accounts, email systems, collaboration tools, and third-party services. A single misconfigured trigger can cascade into simultaneous data theft, business process disruption, and third-party breaches — all from one HTTP request.

### 5. Cloud Attack Timelines Are Measured in Minutes

Once an exposed endpoint or SAS URL is indexed by a scanner, exploitation can follow within minutes. Without detection controls — Logic App run history monitoring, Microsoft Defender for Cloud alerts, and Azure Monitor rules on Storage access — an intrusion may go unnoticed until significant damage has occurred.

## Remediation

| Control | Action |
|---------|--------|
| 🔐 **Trigger Authentication** | Enable Azure AD authentication on the HTTP trigger. Never leave Logic App triggers publicly accessible without auth. |
| ✅ **Parameter Validation** | Validate and allowlist all trigger parameters. Use a Condition or Switch action to reject values outside the expected set. |
| 🪪 **Managed Identity** | Replace SAS URLs with Managed Identity. Grant the Logic App's MI direct RBAC permissions on the storage account — no secrets to leak. |
| ⏱️ **SAS Token Scoping** | If SAS tokens must be used, apply minimum permissions, restrict to specific containers, and set the shortest viable expiry. |
| 🔍 **Secret Scanning** | Scan repos and pipelines for exposed SAS URLs using tools like `truffleHog` or `gitleaks`. |
| 📊 **Diagnostic Logging** | Log every trigger invocation — caller details, parameter values, and outcomes. Alert on unexpected values or anomalous patterns. |
| 🛡️ **Defender for Storage** | Enable Microsoft Defender for Storage to detect bulk downloads, access from unusual locations, or first-time SAS URL usage in real time. |

## How This Helps During Incident Response

Understanding this attack chain directly speeds up investigation when a similar incident occurs in production:

- **Logic App run history is your first stop.** Every trigger invocation is logged under Run History in the Azure portal — showing exactly when the trigger fired, what inputs it received, and which actions executed. This pinpoints the moment of compromise.

- **Storage access logs confirm exfiltration.** Azure Storage diagnostic logs record every read, write, and delete along with the caller's IP and the SAS token used. Correlating these with Logic App run timestamps confirms whether data was accessed or files were planted.

- **An unexpected file in the storage share is an IOC.** Just as the flag file appeared after the tampered trigger, in a real incident an unexplained file in a connected File Share or Blob container is a strong indicator of unauthorised workflow execution — treat it as evidence, not noise.

- **The SAS URL is a forensic artefact.** A SAS URL found in browser history, proxy logs, or SIEM data can be traced back to when it was generated, what permissions it encodes, and whether it has been used from unexpected locations — all valuable for breach scoping.

- **Knowing the attack path cuts triage time significantly.** IR teams familiar with this pattern check the trigger URL → `name` parameter in run inputs → connected storage container in sequence, rather than spending hours ruling out unrelated systems.
